# Tric-Gabay application scenario matrix

Date: 2026-10-25  
Scope: repository-backed application behavior through Batch 9, before physical-device, live-provider, hosted-environment, or deployment validation.

This matrix is comprehensive for the implemented routes, services, database functions, Edge Functions, and automated tests inspected in this repository. It is not a claim that every real-world circumstance has been exercised. Rows marked **Unverified** require a physical device or external provider; rows marked **Policy** need a product-owner decision before behavior should be added.

Status meanings: **Implemented** = protected by code and/or an automated test; **Partial** = safe behavior exists but an important recovery or presentation path is incomplete; **Missing** = the inspected implementation has a confirmed gap; **Unverified** = implemented path cannot be proved locally in this batch.

## State machines and invariants

### Booking and trip

- States implemented: `pending`, `accepted`, `ongoing`, `completed`, `cancelled`.
- Allowed transitions are performed by server RPCs (accept, cancel, start with pickup code, report arrivals/events, complete) and mirrored by local `TripRules` only for isolated unconfigured tests.
- Terminal `completed` and `cancelled` records must never become active again. Duplicate/wrong-state calls fail without a client-side rollback of newer server state.
- Exclusive driver assignment and one-active-booking rules are database invariants. The backend is authoritative after any ambiguous response.
- A lost booking-creation response is recovered by authoritative read plus a locally persisted, one-time recovery request. Identical retries return the same code; a different request cannot rotate it, lockout state is preserved, and plaintext is absent from database audit data.
- Tracking is allowed only for a server-confirmed assigned accepted/ongoing booking; cached state alone is insufficient.

### Driver availability and location

- Availability requires an active, approved, compliant driver and no conflicting lifecycle operation.
- Current location accepts only valid, timely, monotonically newer samples through `publish_driver_location`; history/current-point access is participant/operations scoped.
- Going offline or reaching a terminal trip state must stop the relevant stream and clear the recovery marker. A product-owner retention period for historical location remains an explicit policy decision.

### Payments and refunds

- Payment/refund transitions follow `docs/paymongo-payment-state-machine.md`; provider events are authenticated, atomically deduplicated, identity/amount checked, and monotonic.
- Ambiguous provider outcomes remain reconcilable. Notifications never define financial truth.
- Ledger entries are append-only and triggered from authoritative transitions. Refund reservation/finalization requires finance capability and idempotency.
- Checkout provider creation remains outside the database transaction. Stable provider idempotency per attempt, exact provider-origin/identity validation, an atomic local commit RPC, retried webhooks, and reconciliation narrow—but cannot mathematically eliminate—the cross-system failure window.

### Notifications and administration

- Notifications are a view/communication layer. Opening one is always re-authorized through the router and database.
- Only notification-read acknowledgements are safe for automatic offline replay.
- Admin UI visibility is advisory; capability-specific database and storage policies are the security boundary. Revocation must take effect on the next authoritative action even if the screen is stale.

## Explicitly unresolved or deferred

1. Municipal/product policy for mid-trip suspension, emergency handoff, legal tricycle road restrictions, historical location retention, arbitrary partial refunds, and orphaned/versioned image cleanup.
2. Physical Android lifecycle, permission, background-location, notification-tap, text-scaling, and process-death validation.
3. Live PayMongo test-mode, email, push, Maps/Mapbox outage, and hosted Supabase behavior. Batch 9 passed isolated local Auth/PostgREST/RPC/RLS/Storage service integration; hosted configuration and excluded local Edge Runtime/Realtime behavior remain separate evidence gaps.
4. Production signing, deployment, backup/restore rehearsal against a hosted project, and operational alert routing.

These are not silently treated as passed. They remain outside this batch's explicit local-only boundary.
